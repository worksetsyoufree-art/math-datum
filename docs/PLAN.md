# math-datum: план

Инструментарий локальных систем координат для поверхностей (DXF, позже LandXML): найти СК из справочника
или собрать привязку по парам точек. Kotlin Multiplatform: android, desktop (JVM), web (JS).
Источники требований: `dxf-georef-todo.md` (общий план и UI) и `tin-georef-transforms-todo.md` (математика и проверка).
Просмотр DXF уже есть в соседнем проекте `viewer3d`; здесь только привязка.

## Архитектура

```
:core      чистый Kotlin, без зависимостей (kotlin.math): эллипсоиды, cart, Гельмерт, TM, CrsDef,
           Georef, Localization, DatumFinder           ← прототип готов
:catalog   справочник СК (JSON/PROJJSON) + загрузка, версия, фильтр по региону                    (блок 3)
:app       Compose Multiplatform: экраны Авто / Выбрать СК / По точкам / Проверка                  (блок 7)
viewer3d   (внешний проект) отдаёт SurfaceBounds, вершины, снап; получает Georef                   (блок 6)
```

Единый результат обоих путей — `Georef`: `toWgs84(x, y, z)` / `fromWgs84(p)`.
Поток данных: поверхность → `SurfaceBounds` + `Anchor` → `DatumFinder.find` → `Candidate.toGeoref()`;
либо пары точек → `Localization.localize` → `LocalizedGeoref`. Хранение привязки не входит в ядро.

## Справочник EPSG: что внутри и чему верить

Источник — реестр EPSG через базу PROJ (`proj.db`), то есть те же данные, что на epsg.io (сам epsg.io доступен как перекрёстная проверка). Генерация: `python3 tools/gen_epsg_catalog.py`.

| Показатель | Значение |
|------------|----------|
| актуальных проекционных СК в EPSG | 5346 |
| вошло в справочник | 5021 (методы: TM 9807, TM South Orientated 9808, Ламберт 1SP 9801 и 2SP 9802) |
| не поддерживается | 325: Albers 40, Colombia Urban 32, Cassini 30, Polar Stereographic B 28, Hotine A/B 34, LAEA 21, Oblique Stereographic 19, Lambert West Orientated 15 и ещё ~15 методов; 30 СК с нулевым меридианом не Гринвич (Париж и др.) |
| статус перехода в WGS84 | точный/нулевой сдвиг 2363, параметры из реестра 1926, параметры для другой части территории 200, только сеточный переход 44, перехода в реестре нет 488 |

Проверка:
- Сверка с PROJ: 1006 СК каталога (выборка по методам × статусам × осям × единицам), 3018 точек, максимум 6,3e-7 м (`EpsgCatalogTest`, эталон `tools/gen_epsg_golden.py`). Конвейер PROJ строится из записи каталога независимо от Kotlin.
- Аудит выбора перехода против «выбора по умолчанию» PROJ (`tools/audit_epsg_selection.py`): 2340 из 2340 СК со статусом «точный» совпали до 1 см; из «helmert» 88 % до 1 см, 10 % до 10 м (PROJ берёт другую региональную операцию сопоставимой точности). Аудит нашёл и исправил ошибку выбора через линию смены дат.
- Не сверялось: параметры, которых нет в EPSG (МСК-регионы, МГГТ и т. п.), поэтому они добавляются файлами `datum.json`.

Что дальше по справочнику (по убыванию пользы): остальные методы проекций (Albers, Cassini, Polar Stereographic, Hotine, LAEA, Oblique Stereographic), нулевой меридиан не Гринвич (30), Молодёнский–Бадекас (≈55 СК), составные операции перехода.

## Направление параметров перехода (datum.json)

Параметры Гельмерта в формате справочника приложения не содержат направления. Для файла пользователя (МСК-50, зона 2, МГГТ) обе трактовки дают положение чертежа с расхождением **около 203 м**. Различать их помогает физический признак: при переходе между близкими геодезическими системами эллипсоидальная высота меняется на единицы метров (СК-42 → WGS84 в Москве: +3,4 м), а при неверно прочитанном направлении — на сотни. Для параметров пользователя: «WGS84 → местная» даёт +0,1 м, «местная → WGS84» даёт +219 м, поэтому по умолчанию принято «WGS84 → местная» (как в справочнике приложения). Приложение показывает обе величины и позволяет переключить трактовку (`CrsDef.checkHelmertDirection`). Окончательно подтвердить можно по одной известной точке на чертеже.

## Что показал прототип

Проверено: 51 тест `:core` проходит на JS (Node) и Android unit, 55 — на desktop (JVM; плюс сверка каталога с PROJ и реальные файлы), 14 тестов `:app` — на desktop; без Gradle — `tools/run_jvm_tests.sh`:
- Эталоны PROJ 9.8.1 (UTM и конвейер Красовский + Гельмерт `coordinate_frame` + TM): разница ≤ 1e-8 м
  в Python-зеркале на ±10° от ЦМ; Kotlin-тесты проверяют с допуском 1e-4 м. Положение вне ±10° не проверялось.
- Гельмерт: обратная через транспонирование, не через отрицание параметров; оба соглашения вращений совпали с PROJ `+exact`.
- cart: полюса и ось Земли без мусора; TM: ЦМ 90° и > 180° проходят круговой тест.
- Локализация 8 точек на 10 км, истина — ЦМ рядом с участком: RMS ≈ 1,4 мм (Python), тесты Kotlin ≤ 4 мм.
- Поиск СК: верная СК + X/Y + мм находится первой; далёкий anchor и локальный чертёж 0…1000 не дают «совпал».

- Скорость (desktop JVM): 1e6 точек — прямое преобразование ≈ 1,4 с, обратное ≈ 2,1 с. На слабом Android не измерялось.
- Калибровка поверх СК: участок в ~85 км от ЦМ, поправка 2,5 м + ≈ 4″ — RMS < 0,5 мм против ≥ 5 мм у чистого подобия.

Что это означает для плана:
1. **Предел подобия.** Если участок далеко от ЦМ истинной проекции (20 км), подобие даёт ≈ 7 мм из-за градиента масштаба;
   целевые 1–2 мм достижимы близко к ЦМ либо в режиме `Localization.calibrate` (известная СК + малая поправка).
2. **Коллинеарность** не мешает подобию 2D, только плоскости высоты и 3D. Предупреждение нужно там, не здесь.
3. **Порядок осей.** Справочник — X север / Y восток, CAD — X восток / Y север. `CrsGeoref.swapXY` и перебор 2×2 это учитывают;
   в `localize` поверхность считается CAD (x — восток, y — север).
4. **TM.** Ряды 6-го порядка достаточны около ЦМ; для зон шире ±10° решить в блоке 2 по сверке с PROJ на всех 340 записях,
   при необходимости поднять порядок до 8 (Poder–Engsager).

## Не проверено

- CI на GitHub Actions не запускался (файл написан, команды те же, что прогонялись локально).
- JS-таргет проверен в Node, не в браузере. Находка: в JS `1.0.toString()` даёт `"1"`, поэтому формат JSON и тесты не должны зависеть от текста числа.
- Справочник приложения на 340 записей и регресс против `math` 0.5.5 — вне репозитория; ждут файл и лицензию.
- Приложение на реальном Android-устройстве или эмуляторе (APK собирается, но не запускался).

## Этапы работ

1. **M0 — сделано:** Gradle собирает `:core` на трёх таргетах, 28 тестов зелёные на desktop (JVM), JS (Node) и Android unit; добавлен `.github/workflows/ci.yml` (на GitHub Actions ещё не запускался).
2. **M1 (≈ неделя):** справочник: получить файл и лицензию; генератор эталонов на все записи; сверка ≤ 0,1 мм в 3D; граничные случаи (ЦМ 90°, > 180°, юг, дальше ±3°).
3. **M2 (≈ неделя):** локализация: плоскость высоты, 3D Хорн, «проекция задана», робастные выбросы, `sterea`; стабильность при сдвиге начала 1e6 и масштабе ≠ 1; синтетика 10/50/100 км по B4.
4. **M3 (3–5 дней):** поиск СК: правдоподобие без anchor, предфильтр по регионам, метрики топ-1/топ-3 на 20+ синтетических поверхностях, время на слабом Android.
5. **M4 (≈ 2 недели):** `SurfaceSource` + адаптер `viewer3d`, хранилище привязки, UI на Compose MP (desktop → android → web).
6. **M5:** реальные чертежи, полевая проверка GPS, документация точности.

## Риски

- Лицензия и происхождение справочника (в `CSName` есть Credo и Trimble).
- 277 из 278 проекций нигде открыто не подтверждены; 35 наборов Гельмерта нет в EPSG.
- DXF без единиц и без привязки: автоподбор не работает, остаётся «По точкам».
- Тихие дефекты `math` 0.5.5 нельзя переносить: сверка с ним только как регресс «не хуже».
