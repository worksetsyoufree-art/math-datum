# math-datum

Локализация ГНСС (пары точек WGS-84 ↔ местная система → датум → пересчёты), пересчёты между
государственными системами координат по ГОСТ 32453-2017, а также наборы точек и эталонные результаты
для их проверки.

## Локализация

```
pip install -r requirements.txt

python -m mathdatum localize examples/pairs.csv -o datum.json      # расчёт датума + отчёт по невязкам
python -m mathdatum to-local datum.json examples/wgs_points.csv -o local.csv   # B L h → x y H
python -m mathdatum to-wgs   datum.json local.csv -o wgs.csv                   # x y H → B L h
python -m mathdatum proj datum.json                                 # строка PROJ для QGIS / cs2cs
python -m mathdatum export datum.json --format wkt2 -o datum.wkt    # WKT2 / projjson / jxl (Trimble) / landxml

python -m mathdatum localize examples/pairs.csv --suggest           # + какие точки исключить (по худшему |w|)
python -m mathdatum to-local datum.json examples/wgs_points.csv -o local.csv --quality   # + outside_m;m_plan;m_H
```

`localize` печатает параметры, избыточность, СКО единицы веса, таблицу невязок с нормированными
поправками |w| и ошибками «без точки» (leave-one-out) и предупреждения. Параметры: `--sigma-plan 0.02`,
`--sigma-height 0.03` (априорные СКО, м), `--w-limit 3.29`, `--max-scale-ppm 200`, `--max-rotation-deg 3`.
`to-local` / `to-wgs` перечисляют в stderr точки вне выпуклой оболочки опорных пунктов (экстраполяция);
формат файла без `--quality` прежний (`name;x;y;H` / `name;B;L;h`), с `--quality` добавляются столбцы
`outside_m` (расстояние до оболочки, 0 — внутри), `m_plan`, `m_H` (ожидаемая СКО прогноза, м).

Формат пар (`examples/pairs.csv`): `name;B;L;h;x;y;H;use`. B, L — градусы WGS-84 (или системы
`--gnss-datum`), h — высота ГНСС (эллипсоидальная), x — север, y — восток, H — местная высота. `use`: `both` (по умолчанию), `plan`,
`height` или `none` — точка не участвует в расчёте, но для неё печатается ошибка (контроль).
Необязательные столбцы `sigma_plan;sigma_height` — априорная СКО точки, м (план — на одну координату):
суммарная точность каталога и ГНСС, `√(σ_кат² + σ_ГНСС²)`. Пусто или столбца нет — глобальная σ0
(`--sigma-plan` / `--sigma-height`); старые файлы читаются без изменений. При весах в отчёте есть столбцы σ.

Из Python:

```python
from mathdatum import Pair, localize, LocalizationDatum
d = localize([Pair("R1", 55.05, 39.27, 215.5, -200498.03, 3258049.82, 209.38), ...])
x, y, H = d.to_local(B, L, h)
B, L, h = d.to_wgs(x, y, H)
d.save("datum.json"); d = LocalizationDatum.load("datum.json")
```

Модель (`mathdatum/localization.py`):
1. Рабочая проекция — поперечный Меркатор на эллипсоиде системы ГНСС-измерений (по умолчанию WGS-84)
   с центром в среднем по точкам, k = 1; или заданная (`projection=` / `--projection`, например LDP — см. ниже).
2. План — подобие (сдвиг, разворот, масштаб) относительно взвешенного центроида точек.
3. Высота — наклонная плоскость `H = h + c0 + c1·dN + c2·dE` (по умолчанию) или модель геоида
   (`geoid`, `geoid_plane` — см. «Модель геоида»).

Обе подгонки — взвешенный линейный МНК в замкнутой форме. Вес точки `p = σ0² / σi²` (σ0 — глобальная
σ, σi — своя σ точки; без неё `p = 1`). План: `zc = Σp·z / Σp`, `k = a + ib = Σp·conj(z − zc)·(w − wc) / Σp·|z − zc|²`
(`z = N + iE`, `w = x + iy`); высота — плоскость по данным, центрированным на взвешенное среднее.
При равных весах результат совпадает с невзвешенным (до округления, < 1e-12 относительно). Если точек мало, модель упрощается: 1 точка в плане
даёт только сдвиг; 1–2 точки по высоте или точки на одной линии дают только сдвиг по высоте.

### Надёжность

Только диагностика: точки автоматически не исключаются (`suggest_exclusions` лишь предлагает
исключать худшую точку итеративно).

- **Избыточность:** `r_plan = 2n − 4` (сдвиг `2n − 2`), `r_height = n − 3` (сдвиг `n − 1`). При `r = 0`
  невязки нулевые, контроля нет — предупреждение.
- **Нормированные поправки (тест Баарда):** `w = v / (σ0·√q_vv)`, `q_vv = 1/p − aᵀQa`, `Q = (AᵀPA)⁻¹`,
  σ0 — априорная СКО единицы веса на одну координату (0.02 м в плане, 0.03 м по высоте); при `p = 1`
  это `v / (σ·√(1 − aᵀQa))`. `Σ p·q_vv = r`. `|w| > 3.29` — точка подозрительна. В плане `q_vv` по x и y
  одинаков: `1/p − 1/P − ρ²/S`, `ρ` — расстояние до взвешенного центроида, `P = Σp`, `S = Σp·ρ²`. Подсветка «невязка > 3·СКО» не годится: `max|v| ≤ √n·СКО`, при `n ≤ 9` она не срабатывает,
  а выброс ещё и раздувает СКО. Для 6 пунктов и σ = 2 см минимальная надёжно обнаруживаемая ошибка ≈ 10 см;
  соседние близкие пункты тоже получают большие |w| («размазывание»), виноват — худший.
- **Ошибка без точки (leave-one-out):** датум пересчитывается без точки (в той же рабочей проекции)
  и даёт ошибку прогноза в ней; равна `v / (p·q_vv)`. Если без точки модель вырождается или меняется
  (например, плоскость → сдвиг) — `None`, «нельзя проверить». Для контрольных точек (`use = none`) —
  сама невязка, `q_vv = 1/p + aᵀQa`.
- **Ковариации и точность прогноза:** `covariance_plan()`, `covariance_height()` = `σ²·Q` (априорная σ0
  или `posterior=True` — апостериорная `s0 = √(vᵀPv/r)`); `prediction_sigma(B, L)` = `σ·√(aᵀQa)`
  (план — радиальная по x и y).
- **Веса:** точка с большой σ почти не влияет на датум (и её ошибка не помечается, если укладывается в
  её σ), точка с малой σ «притягивает» решение. Использованные σ и веса — в `Residual.sigma_plan`,
  `sigma_height`, `p_plan`, `p_height`.
- **Экстраполяция:** `outside_distance(B, L)`, `quality_wgs`, `quality_local` — расстояние до выпуклой
  оболочки опорных пунктов плана (0 внутри).
- **Правдоподобие:** `|scale_ppm| > 200` или `|разворот| > 3°` — предупреждение о перепутанных осях или
  системах (пороги — параметры `localize`). Разворот до ~1–1.5° бывает законно — сближение меридианов при
  удалённом осевом меридиане МСК (4 из 83 регионов `data/geodetic`), поэтому порог 3°, а не 1°.

Предупреждения (`warnings`: `code`, `message`, `point`), кофакторы, оболочка, использованные σ и веса
и диагностика невязок сохраняются в JSON датума. Старые JSON читаются: недостающие поля — `None`,
пересчёты работают, точность и экстраполяция не определены.

Тесты: `pip install pytest && python -m pytest tests` (634 теста, включая 83 региона из `data/geodetic`):
`tests/test_localization.py` — локализация и надёжность, `tests/test_geoid.py` — сетки геоида и модели высот,
`tests/test_ldp.py` — малоискажающая проекция, `tests/test_export.py` — экспорт (pyproj по 83 регионам, схемы JobXML и LandXML),
`tests/test_datums.py` — пересчёты между системами
(контрольный пример ГОСТ, туда-обратно по всем 56 парам систем, сверка с PROJ по 7 параметрам, BLH ↔ XYZ,
Гаусс–Крюгер и своему поперечному Меркатору, задачи `helmert_7p` 83 регионов, датум ГНСС в локализации и CLI).

### Датум ГНСС-измерений

По умолчанию пары считаются заданными в WGS-84 — как раньше, результаты не меняются. Если ГНСС-координаты
в другой системе (ПЗ-90.11 от приёмника ГЛОНАСС, ГСК-2011, ITRF-2008, СК-42…), её указывают явно:

```
python -m mathdatum localize pairs_pz.csv -o datum.json --gnss-datum PZ-90.11
python -m mathdatum to-local datum.json wgs.csv -o local.csv --gnss-datum WGS-84   # точки в WGS-84 → ПЗ-90.11 → местные
python -m mathdatum to-wgs   datum.json local.csv -o wgs.csv --gnss-datum WGS-84   # результат в WGS-84
```

```python
d = localize(pairs, gnss_datum="PZ-90.11")        # рабочая проекция на эллипсоиде ПЗ-90
x, y, H = d.to_local(B, L, h, datum="WGS-84")     # точка в другой системе: сначала пересчёт по ГОСТ
```

Рабочая проекция строится на эллипсоиде этой системы, координаты в WGS-84 **не переводятся**. На участке
переход между системами по 7 параметрам — это почти точно сдвиг, разворот, масштаб и наклон высот, их и так
поглощают подобие и плоскость высот: разница двух вариантов на участке 5 км ≤ 1 мм для СК-42 (сдвиг ~160 м)
и ~1 мкм для WGS-84 / ГСК-2011 (`tests/test_datums.py`). Предварительный пересчёт лишь добавил бы погрешность
самих параметров (для СК-42 — до метров из-за локальных искажений сети). Система сохраняется в JSON датума
(`gnss_datum`); в старых JSON поля нет — при рабочей проекции на WGS-84 считается WGS-84, иначе пересчёт
из других систем недоступен. `--gnss-datum` у `to-local` / `to-wgs` — система точек файла, если она не
совпадает с системой датума (пересчёт по 7 параметрам, путь печатается в stderr).

### Модель геоида (высоты)

Модель высоты задаётся параметром; по умолчанию — прежняя `plane`, результаты не меняются.

| Модель | Формула | Параметров | Избыточность |
|---|---|---|---|
| `plane` | `H = h + c0 + c1·dN + c2·dE` | 3 (мало точек → `shift`, 1) | `n − 3` |
| `geoid` | `H = h − N(B, L) + c0` | 1 | `n − 1` |
| `geoid_plane` | `H = h − N(B, L) + c0 + c1·dN + c2·dE` — остаточная плоскость по `H − (h − N)` | 3 (мало точек → `geoid`, 1) | `n − 3` |

`N(B, L)` — высота геоида / аномалия высоты из сетки на эллипсоиде системы ГНСС (`gnss_datum`). Вся диагностика
(Q, w, leave-one-out, ковариации, СКО прогноза, веса, `suggest_exclusions`) работает для всех моделей: после
вычитания N подгоняются разности `H − (h − N)` той же формулой, меняется только число параметров.
СКО прогноза не включает ошибку самой модели геоида.

```
python -m mathdatum localize pairs.csv -o datum.json --gnss-datum PZ-90.11 --geoid region.ggf          # geoid_plane
python -m mathdatum localize pairs.csv -o datum.json --geoid region.ggf --height-model geoid --geoid-interpolation bicubic
python -m mathdatum to-local datum.json wgs.csv -o local.csv --geoid region.ggf     # если сетка не рядом с datum.json
python -m mathdatum geoid region.ggf --at 55.75,37.62                                # сведения о сетке и N в точке
python -m mathdatum geoid us_nga_egm08_25.tif --crop 55,56.5,36.5,39 -o site.gtx    # вырезка / перевод формата
```

```python
from mathdatum.geoid import read_grid
d = localize(pairs, gnss_datum="PZ-90.11", height_model="geoid_plane", geoid=read_grid("region.ggf"))
d = LocalizationDatum.load("datum.json", geoid="region.ggf")   # без geoid — ищет файл рядом с JSON и в текущем каталоге
```

- **Форматы сеток** (`mathdatum/geoid.py`, в Kotlin `Geoid.kt`):
  - **GGF** (Trimble Grid Factory, основной формат полевого ПО Trimble) — little-endian, заголовок 146 байт:
    подпись `TNL GRID FILE`, имя модели, `latMin, latMax, lonMin, lonMax, dlat, dlon` (float64), `rows, cols`
    (int32), NODATA (смещение 120, 0 — не задано), масштаб (128), 10 байт флагов (136; смысл неизвестен — у
    известных файлов `02 00 80 00 02 08 02 01 00 00`, иначе предупреждение); данные float32 (или int16 — по
    размеру файла) **строками с севера на юг**, в конце — min/max. Открытого описания нет, раскладка
    восстановлена по файлам (OSM wiki «Trimble GGF», разбор EGM08-R61.GGF) и сверена с EGM2008 (ниже).
  - **GTX** (NOAA / PROJ, big-endian, строки с юга, NODATA −88.8888);
  - **ISG** 1.0 / 2.0 (International Service for the Geoid, текст; углы в градусах или DMS, `node offset`);
  - **GeoTIFF** сеток PROJ (cdn.proj.org; без сжатия / deflate, предиктор 1–3) — только Python; для Kotlin и веба
    переводится в GGF/GTX командой `geoid … -o`.
- **Интерполяция:** `bilinear` — явная формула по долям ячейки (узлы и края сетки — без вырождения),
  `bicubic` — свёртка Кейса (a = −0.5) по 16 узлам (квадратичную поверхность воспроизводит точно; в крайней
  ячейке — ошибка). Python и Kotlin дают одинаковые значения (до 1e-12 м, сверка эталонами).
- **Ошибки, а не тихое отключение поправки** (баг gsimath, `results/gsimath-0.5.5/REPORT.md`, п. 1): точка вне
  сетки, NODATA среди нужных узлов, нет файла сетки или другая SHA-256 — исключение `GeoidError` (Kotlin —
  `GeoidException`). Прямой и обратный пересчёт симметричны: `h = H + N(B, L) − (c0 + c1·dN + c2·dE)`,
  N берётся в той же точке (B, L плана), туда-обратно < 1e-6 м.
- **Датум хранит ссылку, не сетку:** `"geoid": {"file": "region.ggf", "sha256": "…", "interpolation": "bilinear"}`.
  Старые JSON (без поля) читаются как прежде; строка PROJ получает шаг `vgridshift` (PROJ читает GTX/GeoTIFF).
- **Проверка на реальных сетках** (разово, файлы не в репозитории): ридер GeoTIFF/GTX против PROJ `vgridshift`
  на `us_nga_egm96_15.tif`, `egm96_15.gtx`, `us_nga_egm08_25.tif` (5005 точек по миру, с переходом через 180°) —
  расхождение ≤ 8e-13 м. GGF EGM2008 1′×1′ (регион R61: 41–79° с. ш., 103–120° в. д.): в общих узлах 5′ совпадает
  с `us_nga_egm08_25.tif` точно (float32), в 20 000 случайных точек — СКО 1.9 мм, максимум 2.9 см (разное разрешение
  сеток); с EGM96 — СКО 0.56 м (разница моделей); при обратном порядке строк было бы 17 м.
- **Тестовые сетки** `tests/data/geoid/` (≤ 9 КБ, `python tools/make_geoid_test_grids.py`): аномалия высоты участка
  RU-MOW из блока `truth` генератора `data/geodetic` (GGF, GTX, ISG), она же с «бугром» 0.5 м (неплоская часть), и
  сетка 5×6 с NODATA. На них: с «бугром» `plane` даёт ошибку на контрольных 4.9 см, `geoid_plane` с верной сеткой —
  0.8 см; `geoid` с неверной сеткой — остатки 4.7 см и подозрительные точки; по всем 83 регионам сетка по `truth`
  (строится в тесте) даёт в модели `geoid` ошибки на контрольных в пределах шума и `c0 ≈ 0`.

## Экспорт датума (WKT2, PROJJSON, Trimble JobXML, LandXML)

```
python -m mathdatum export datum.json --format wkt2 -o datum.wkt       # QGIS / GDAL / pyproj
python -m mathdatum export datum.json --format projjson -o datum.json
python -m mathdatum export datum.json --format jxl -o site.jxl          # Trimble JobXML 6.30 (+ контрольные точки в stderr)
python -m mathdatum export datum.json --format landxml -o site.xml       # LandXML 1.2, WKT2 в ogcWktCode
```

Подробно — `docs/export.md` (`mathdatum/export.py`, в Kotlin `Export.kt`, в вебе — кнопки в разделе 2):

- **WKT2 / PROJJSON:** план — `DERIVEDPROJCRS` из стандартных методов EPSG (TM 9807 + Similarity transformation 9621),
  при развороте < 0.1 мм на объекте — свёрнут в обычный `PROJCRS` (k0·масштаб); высота — `BOUNDCRS` с методом
  «PROJ-based operation method» (плоскость, `vgridshift` для геоида; GGF/ISG → предупреждение и имя `.gtx`), т. к. для
  плоскости от эллипсоидальной высоты метода EPSG нет. Оси — восток (y), север (x). pyproj на всех 83 регионах
  воспроизводит `to_local` и `to_wgs` до 1e-8 м.
- **Trimble JobXML:** TM с k0·масштаб (масштаб сворачивается точно), горизонтальная корректировка — поворот вокруг
  (tx, ty) без сдвига и масштаба, вертикальная — InclinedPlane / GeoidModelAndInclinedPlane (GGF по имени).
  Знак разворота взят по Trimble Access Calculations Reference, но однозначно там не задан: при обратной трактовке
  ошибка `2·R·sin|θ|` — она печатается вместе с контрольными точками (x, y и x′, y′ при обратном знаке) для проверки
  на контроллере. Схема 6.30 — валидна.
- **LandXML 1.2** параметров локализации не имеет — WKT2 передаётся в `ogcWktCode` (с предупреждением).
- **Закрытые форматы** (Trimble .cal/.dc, Topcon .gc3/.tp3, Carlson .loc, Leica, gsimath) не пишутся — ошибка со
  ссылкой на раздел «Что нужно для поддержки» в `docs/export.md` (какие образцы файлов и отчёты нужны).

## Малоискажающая проекция (LDP) под объект строительства

Строителю нужно, чтобы расстояние на плане равнялось расстоянию на местности. `mathdatum/ldp.py` подбирает
проекцию, у которой суммарное искажение длины по объекту минимально:

```
δ = k(B, L) · R/(R + h) − 1,     R = √(M·N) = a·√(1 − e²)/(1 − e²·sin²B)      (1 ppm = 1 мм/км)
```

k — масштаб проекции в точке, R/(R + h) — высотный множитель (h — эллипсоидальная высота). Для поперечного
Меркатора k ≈ k0·(1 + y²/(2R²)): на высоте 500 м эллипсоид «короче» местности на 78 ppm, и k0 ≈ 1.000078 это компенсирует.

```
python -m mathdatum ldp examples/ldp_site.csv -o ldp.json --map map.csv --map map.geojson
python -m mathdatum ldp examples/ldp_route.csv --tolerance 20 --type tm -o route.json   # трасса 150 км → 2 зоны
python -m mathdatum ldp site.geojson --dem relief.gtx --height-type normal --geoid geoid.gtx
python -m mathdatum localize pairs.csv -o datum.json --projection ldp.json [--zone 2]    # LDP как рабочая проекция
```

- **Вход:** контур — CSV `name;B;L[;h | ;H]` (полигон, если первая вершина повторена в конце, иначе трасса; `--kind`)
  или GeoJSON (Polygon, LineString, Feature/FeatureCollection; z — высота). Высоты: сетка рельефа `--dem`
  (GTX/GGF/ISG/GeoTIFF — те же читатели, что у геоида), иначе высоты вершин (по сторонам — линейно, внутри полигона —
  обратные расстояния), иначе `--height`. Нормальные высоты (`H` или `--height-type normal`) переводятся в
  эллипсоидальные `h = H + N` по `--geoid`; без сетки N = 0 и предупреждение (0.157 ppm на метр N).
- **Система по умолчанию — ГСК-2011** (`--datum`): по Правилам установления МСК местные системы строятся относительно
  ГСК-2011, а численно выбор эллипсоида почти ничего не меняет — ГСК-2011 и WGS-84 дают одинаковые k0 до 1e-8 и
  max|δ| до 0.01 ppm (`test_ellipsoid_choice_is_negligible`). Координаты B, L при этом не пересчитываются.
- **Выборка:** полигон — центры ячеек сетки с шагом `--step` (по умолчанию габарит/50; вес — площадь) и точки контура
  (только для экстремумов), трасса — точки через `--step` (длина/200; вес — длина). Отсюда «доля площади / длины в допуске».
- **Подбор (TM):** `c_i = k_i(k0 = 1)·R_i/(R_i + h_i)`; критерий `minimax` (по умолчанию) — `k0 = 2/(c_min + c_max)`,
  `max|δ| = (c_max − c_min)/(c_max + c_min)`; `rms` — `k0 = Σw·c/Σw·c²`. Осевой меридиан — перебор 121 значения в
  пределах объекта ± 300 км и золотое сечение: L0 может уйти за объект, тогда рост масштаба TM гасит наклон рельефа
  (полоса 30×4 км с подъёмом 100 м на восток: L0 в 158 км западнее, ±2.1 ppm вместо ±7.8 при L0 по центру).
  Затем L0 и широта начала (центр объекта) округляются до 1′ (`--round-angle`), k0 — до 1e-6 (`--round-k0`),
  статистика — с округлёнными. Можно задать `--lon0/--lat0/--k0/--x0/--y0`.
- **Ложные смещения:** x0 кратно 10 км так, что x ≥ 5 км; y0 кратно 100 км так, что y ≥ 5 км и y > max x + 20 км
  (например, x0 = 20 000, y0 = 100 000: x ≈ 10–30 тыс., y ≈ 90–110 тыс.) — не спутать с ГК (7 знаков с номером
  зоны), UTM (x ≈ 6·10⁶) и МСК, а x — с y.
- **Косая проекция Меркатора (omerc, Хотин)** — `--type omerc` или `auto` (по умолчанию: если TM не укладывается,
  пробуется omerc): азимут центральной линии — по главной оси точек, затем Нелдер–Мид по азимуту и сдвигу линии;
  формулы как `+proj=omerc` (вариант B, `+gamma = +alpha`), сверены с PROJ: координаты до 1e-6 м, обратная — 1e-10°,
  масштаб — 1e-9 (|α| = 90° PROJ считает иначе — LDP его не выдаёт). Только Python; для локализации и Kotlin/веб — TM.
- **Выход:** параметры (PROJ-строка, JSON `mathdatum-ldp` версии 1), статистика min/max/mean/RMS/max|δ| и доля в
  допуске, сравнение с ГК 6° и UTM (каждая точка в своей зоне), замечания; `--map *.csv` — сетка узлов
  (`row;col;B;L;h;zone;k;height_factor;ppm;dist_m`), `--map *.geojson` — контур, границы зон и изолинии
  (marching squares, «круглый» шаг и ±допуск).
- **Зоны:** если одна проекция не укладывается, трасса делится по пикетажу, полигон — полосами по восточной
  координате (omerc — поперёк оси). Жадно: каждая зона — наибольший участок, для которого минимаксная TM даёт
  max|δ| ≤ допуска (бинарный поиск по точкам выборки, соседние зоны делят граничную точку); при n зонах пробуются
  n равных. Если перепад высот сам по себе больше допуска — предупреждение (нужны зоны по высоте), при
  недостижимости — без зон.
- **Локализация в LDP:** `localize(pairs, projection=ldp_projection)` (CLI `--projection ldp.json [--zone n]` или
  `tm:lon0=…,k0=…,x0=…,y0=…`) — рабочая проекция с k0, x0, y0 вместо TM по центру с k = 1; поля `k0`, `x0`, `y0` в JSON
  датума (в старых их нет → 1, 0, 0; строка PROJ прежняя). JSON ldp читается с лишними полями и без необязательных.

Примеры (`tests/test_ldp.py`):

| Объект | LDP | max\|δ\| | ГК 6° | UTM |
|---|---|---|---|---|
| квадрат 20×20 км, h = 500 м (55.5°, 38°) | TM, L0 = 38°00′, k0 = 1.000078, x0 = 20 000, y0 = 100 000 | 0.93 ppm, 100 % площади | −43.8…−12.3 ppm | −444…−412 ppm |
| `examples/ldp_site.csv` (383 км², h 196–248 м) | TM, L0 = 39°12′, k0 = 1.000033 | 3.7 ppm | −34…−24 ppm | ≈ −430 ppm |
| трасса 150 км W–E, h = 200 м | одна TM: ±35 ppm (42 % длины в допуске) → 2 зоны по 75 км, ≤ 9.3 ppm; omerc одной зоной — 0.3 ppm | | −31…+170 ppm | −431…−231 ppm |
| `examples/ldp_route.csv` (150 км, H 140–230 м) | одна TM: ±39.9 ppm → 2 зоны TM, ≤ 10.3 ppm | | −27…+132 ppm | −427…−268 ppm |

Интеграция: 8 пунктов на участке 20×20 км на высоте 500 м, местные координаты «плоскость = местность»
(топоцентрические на высоте участка): с рабочей TM k = 1 масштаб подобия +77.7 ppm, с LDP — −0.36 ppm при той же СКО.

Проверки: масштаб и сближение меридианов TM против `Proj.get_factors` (3 эллипсоида, до 4.5° от осевого — 1e-9 и 1e-8°),
k = k0 на осевом меридиане (1e-13), рост ≈ y²/(2R²), R = √(MN) и R/(R + h) против хорд XYZ по меридиану и параллели,
δ по выборке через строку PROJ (pyproj) совпадает с отчётом.

## Пересчёты между системами (ГОСТ 32453-2017)

`mathdatum/datums.py` (и `Datums.kt` в Kotlin — те же формулы 1:1):

| Система | Код | Эллипсоид | Параметры |
|---|---|---|---|
| СК-42, СК-95 | `SK-42`, `SK-95` | Красовского | → ПЗ-90.11, прил. А.1, А.3 |
| ГСК-2011 | `GSK-2011` | ГСК-2011 | → ПЗ-90.11, прил. А.5 (эпоха 2011.0) |
| ПЗ-90, ПЗ-90.02, ПЗ-90.11 | `PZ-90`, `PZ-90.02`, `PZ-90.11` | ПЗ-90 | прил. В.1, Б.1 (эпоха 2010.0) |
| WGS-84 (G1150) | `WGS-84` | WGS-84 | → ПЗ-90.11, прил. Г.1 |
| ITRF-2008 | `ITRF-2008` | GRS80 | ПЗ-90.11 →, прил. Д.1 (эпоха 2010.0) |

```
python -m mathdatum systems                                                    # системы и параметры
python -m mathdatum transform sk42.csv -o wgs.csv --from СК-42 --to WGS-84     # B;L;h → B;L;h
python -m mathdatum transform gk.csv -o pz.csv --from SK-42 --to PZ-90.11 --in gk --out-format xyz
python -m mathdatum transform wgs.csv -o msk.csv --from WGS-84 --to SK-42 --out-format "tm:lon0=38.48333,x0=-5712900.566,y0=1250000"
python -m mathdatum transform mdvj.csv -o out.csv --from ITRF-2008 --to PZ-90.11 --in xyz --out-format xyz --epoch 2005 --target-epoch 2013.9
```

Форматы: `blh` — `name;B;L;h`; `xyz` — `name;X;Y;Z`; `gk` — `name;x;y;H`, Гаусс–Крюгер 6° (`gk:7` — зона 7);
`tm:lon0=…,lat0=…,k0=…,x0=…,y0=…` — свой поперечный Меркатор («МСК-подобные» системы; x0 — на север, y0 — на восток).
H плоских форматов — геодезическая высота; при подстановке нормальной план искажается на ~ζ·2·10⁻⁵ (0.5 мм при ζ = 25 м).

```python
from mathdatum import datums
datums.transform_blh(B, L, h, "СК-42", "WGS-84")             # через ПЗ-90.11 (путь — datums.find_path)
datums.transform_xyz(xyz, "ITRF-2008", "PZ-90.11", epoch=2005.0, velocity=v, target_epoch=2013.9)
datums.blh_to_xyz(B, L, h, "krass"); datums.xyz_to_blh(X, Y, Z, "SK-42")
x, y = datums.gk_forward(B, L, "krass")                       # y = n·10⁶ + 500 000 + E
B, L = datums.gk_inverse(x, y, "krass")                       # зона — по первым цифрам y
datums.TransverseMercator("krass", lon0=38.48333, x0=-5712900.566, y0=1250000).forward(B, L)
```

- **Формула ГОСТ** (поворот системы координат, малые углы; в PROJ `+convention=coordinate_frame`):
  `X2 = (1 + m)·R·X1 + ΔX`, `R = [[1, ωz, −ωy], [−ωz, 1, ωx], [ωy, −ωx, 1]]`. **Обратный переход** — точное
  обращение `X1 = (Rᵀ + ω·ωᵀ)·(X2 − ΔX) / ((1 + |ω|²)(1 + m))`: туда-обратно сходится до 1e-9 м. Упрощённое
  обращение сменой знаков параметров отличается на `(|ω| + |m|)·|ΔX|` — до 0.6 мм для СК-42; PROJ обращает через
  `Rᵀ` (расхождение ≤ 0.1 мм).
- **Цепочки** — кратчайший путь по графу параметров (все наборы ГОСТ связаны через ПЗ-90.11): СК-42 → ПЗ-90.11 →
  WGS-84 — прямой А.1 и обратный Г.1.
- **Эпоха** — только то, что определено ГОСТ: если заданы эпоха координат и скорость пункта (м/год), перед шагом
  с эпохой параметров (А.5, Б.1, Д.1) координаты линейно переносятся на неё, в конце — на целевую эпоху. Моделей
  скоростей нет; без скорости координаты считаются отнесёнными к эпохе параметров. Скорость пункта между
  системами не меняется (как в контрольном примере ГОСТ).
- **Почему свои формулы, а не PROJ:** Kotlin-порт обязан давать тот же результат без PROJ, поэтому эталоном служит
  одна реализация, повторённая 1:1, а PROJ — независимая проверка в тестах (7 параметров — до 1e-6 м,
  BLH ↔ XYZ — до 1e-6 м, Гаусс–Крюгер и поперечный Меркатор — до 1e-6 м).
- **Параметры** совпадают с `data/geodetic/gost_32453_parameters.json` (проверяется тестом). У СК-95 (прил. А.3)
  в файле был знак ωy = −0.00354″; исправлен на +0.00354″: наборы А.1, А.3, В.1, Г.1 — композиция параметров
  ГОСТ Р 51794-2008 (→ ПЗ-90.02) с прил. Б.1 (ωy = +0.00354″), и все остальные наборы с ней сходятся до последнего
  знака (`test_parameters_are_composition_with_b1`). Разница — ~0.2 м.
- **WGS-84:** в ГОСТ (и в файле данных) параметры есть только для реализации G1150 (прил. Г.1); для G1762 и более
  новых своих параметров нет, они не добавлены. Свой набор можно передать в `find_path(..., transformations=…)`
  или `transform_xyz(..., path=…)`.
- **Контрольный пример ГОСТ** (прил. Е, пункт Менделеево) воспроизводится полностью: шаг 1 (перенос эпохи
  2005 → 2010) — 1e-9 м, шаг 2 (ITRF-2008 → ПЗ-90.11, обратный Д.1) — 4.3e-5 м (в ГОСТ значения до 0.1 мм),
  шаг 3 (2010 → 2013.9 той же скоростью) — 2.3e-4 м (в ГОСТ — до 1 мм).

## Kotlin Multiplatform

`kmp/` — та же локализация и пересчёты между системами на Kotlin для Android, iOS, Web и Desktop,
с тестами против Python-эталона. Готовое веб-приложение: откройте `kmp/web-dist/index.html` в браузере.
Подробности — в `kmp/README.md`.

## Данные

- `data/nist_l2/` — эталонные МНК-подгонки NIST (прямая, плоскость, окружность, сфера, цилиндр, конус).
- `data/synthetic/` — машиностроение: МНК-плоскость, плоскостность по минимальной зоне, система датумов 3-2-1, совмещение с номинальной моделью.
- `data/geodetic/` — геодезия по 83 субъектам РФ: 7 параметров СК-42 → ПЗ-90.11 (ГОСТ 32453-2017), локализация ГНСС в местной системе.
  Генератор и проверка используют `mathdatum.datums` (проверка — дополнительно независимо через PROJ).

Описание форматов: `data/README.md`, `data/geodetic/README.md`.

```
pip install -r requirements.txt
python tools/verify_cases.py      # NIST + synthetic
python tools/verify_geodetic.py   # регионы РФ
```

- `examples/ldp_site.csv`, `examples/ldp_route.csv` — контуры для `ldp` (площадка с высотами вершин, трасса 150 км).
